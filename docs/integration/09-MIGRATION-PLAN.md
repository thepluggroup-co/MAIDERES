# 09 — Migration Plan

Written after Phase 0 (discovery, docs 00–08) and after both decision gates were resolved by the product owner:

- **Decision gate 1** (two Supabase projects): `maidere-connect`'s own project was confirmed disposable, no real user data. **MAIDERES's Supabase project is the single source of truth.**
- **Decision gate 2** (three auth systems): resolved the same way — one identity store (MAIDERES's Supabase Auth), consumed directly by both frontends.

Unlike a typical Phase 1 document written before any code moves, most of the plan below has **already been executed and verified** by the time this doc was written — work proceeded incrementally, each slice tested, rather than waiting for a full paper plan. This document records what was actually done, in what order, and what's left.

## What has been executed (in order)

1. **Auth unification** — migration `0026` (`handle_new_user()` trigger bootstraps a `profiles` row at signup, role `apprenant`, never staff); `apps/api`'s role-enum drift (`technicien`/`livreur` vs the real `apprenant`) fixed as a prerequisite bug; `GET /api/profile/me` extended to return derived identity (`is_staff`/`client_id`/`prestataire_id`); `maidere-connect` repointed at MAIDERES's Supabase project, its signup/login flow rewritten to provision a `clients`/`prestataires` record via the API instead of its own (now-abandoned) database trigger; route guards added so a prestataire account can't land on `/espace` and vice versa.
2. **Self-service provider data** — migrations `0027`/`0028`: `offres`, `promotions`, `realisations` tables (the one genuinely new concept `maidere-connect` had that MAIDERES core didn't), plus self-service columns on `prestataires` (`ville`, `metier`, `bio`, `disponible`, `zones_couverture`). New `apps/api` routes (`offresRouter`/`promotionsRouter`/`realisationsRouter`) and a new unauthenticated `publicRouter` (`/api/public/*`) for anonymous directory browsing. `maidere-connect` rewired to consume these instead of querying Supabase directly.
3. **Live validation** — real credentials obtained, migrations `0000`–`0030` applied to the live project, and the full master-prompt §74 scenario (signup → demande → matching → intervention → avis → reply → public storefront) run against real infrastructure with real Supabase Auth accounts, not mocks. Passed; test data cleaned up afterward.
4. **Demande/matching self-service + avis** — turned out to need almost no new backend work (`POST/GET /api/demandes` and `POST /api/avis` already supported client self-service correctly). Added the one real gap: migrations `0029`/`0030` (`avis.reponse` column + RLS so the matched prestataire, and only that prestataire, can reply). New `maidere-connect` pages for demande creation/tracking and a rewritten avis flow (contextual review from a completed matching, not a free-standing form against any provider).
5. **Shared contracts (`packages/contracts`)** — master-prompt §8. Canonical Zod schemas/types for every business entity, enum values guarded against drift from the actual SQL migrations by an automated test. `apps/api`'s core request-lifecycle routes (`categories`, `prestataires`, `clients`, `demandes`, `matchings`, `avis`) and `apps/web`'s corresponding hooks now import from this package instead of each declaring their own copy.
6. **Integration test suite fixed and green live** — `apps/api/src/__tests__/integration/*.test.ts` (16/16) run against the live project. Found and fixed two real, pre-existing bugs never caught before because no live database existed to run them against: a `profiles` insert missing its (default-less) `id` column in `commission-config.integration.test.ts`, and two orphaned `profiles` rows (no matching `auth.users`, blocking new signups via the `email` unique constraint) left from an earlier partial run.
7. **Browser-verified `maidere-connect`** (Playwright) — caught and fixed a real routing bug no API test could have found: `espace.demandes.tsx` was silently treated as an implicit parent layout by TanStack Router (same-prefix filenames nest by convention) with no `<Outlet/>`, so navigating to its children changed the URL but kept showing the old page. Fixed by renaming to `espace.demandes.index.tsx`, matching the `espace.tsx`/`espace.index.tsx` pattern already used elsewhere in the codebase.
8. **Event/notification wiring (Phase 8, master-prompt §30/§32)** — a `notifier()` service that always persists to `notifications_log` (the durable record) and attempts delivery via the existing `sms.service.ts` (safe no-op/dry-run when Africa's Talking isn't configured, matching existing conventions). Wired into the four matching-lifecycle transitions and review creation: prestataire notified on a new proposal, client notified on acceptance and on completion (directly driving the review flow), the proposing operator notified on refusal/failure so they can re-dispatch, and the prestataire notified when they receive a review. Verified both by a dedicated unit test (6 cases: success, SMS failure, missing phone, un-wired channels, log-write failure, thrown exception — never propagates) and live against the real project (4 real `notifications_log` rows created and correctly marked `envoye`, real enum/FK constraints satisfied).
9. **`packages/contracts` migration completed** — the remaining route schemas (`sla_config`, `commission_config`, `transactions`, `interventions`, `offres`, `promotions`, `realisations`) now import from the shared package too; every `apps/api` business route (`admin.ts` excepted — RBAC, not a marketplace entity) is on canonical, centrally-defined validation. Fixed one real mismatch caught in the process (`transactions`' contract wrongly allowed client-supplied `statut_paiement`/`ref_notchpay`, which the route never accepted). Closing this dropped `apps/api`'s own coverage percentage below its 50% gate — not a real regression (all 87 tests still pass; the validation logic is now tested once, well, in `packages/contracts`, rather than diluted across route files) — closed properly by adding real tests for the three routes' cross-field business rules (`sla_config`'s seuil<delai, `commission_config`'s pourcentage≤100, `transactions`' realise-only creation) rather than padding or lowering the threshold.

## `maidere-connect`/`apps/web` — contracts alignment + a real bug found

Comparing `maidere-connect`'s manually-mirrored types (`src/lib/maideres-api.ts`) against `packages/contracts` surfaced a live bug, not just a documentation gap: the DB's `demande_statut` enum has 6 values including `en_cours` (set by the `sync_intervention_statut` trigger, 0009, once a matched intervention moves past `planifiee` — never a direct API transition, see `DEMANDE_STAFF_TRANSITIONS`), but `maidere-connect`'s `Demande["statut"]` type only had 5, and the same gap existed independently in `apps/web`'s `Demandes.tsx`/`Dashboard.tsx` status-label maps (predates this session — `en_cours` was added to the enum in migration `0007`, long before any of this work started). Any demande whose matched intervention had progressed past `planifiee` would render an undefined/blank status badge in both frontends. Fixed in both: type widened, label/tone maps given an `en_cours` entry. `Offre`/`Promotion`/`Realisation`/`Matching` also widened with the optional fields the self-service (authenticated) endpoints return but the public ones omit — additive, no behavior change. `maidere-connect` build + both apps' typecheck/tests verified after.

## `apps/shop` deprecation — actioned

`05-FRONTEND-MAPPING.md` recommended retiring `apps/shop` (superseded by
`maidere-connect`). Actioned: the app, its CI build job, and its
`.vercelignore`/CLAUDE.md references have been removed. Nothing in
`apps/api`/`packages/*` depended on it (its NotchPay/OTP wiring was
already dead code per Phase 0/1, never rewired past Phase 4 planning).

## Data migration note (§71/§72)

No data migration from `maidere-connect`'s old project was needed or performed — it was confirmed to hold no real users. The "migration" that happened was schema-only (adding tables/columns to MAIDERES's project) and code-only (repointing `maidere-connect`'s client). Row-count reconciliation (§72) does not apply here for that reason; it would apply if a future decision surfaces real data in that old project that hadn't been checked.
